# 上下2ペイン化とコピー/移動機能 — 設計スペック

**日付**: 2026-07-06
**ステータス**: 設計確定、実装フェーズ着手待ち

---

## 背景と現状

zurari は C#/.NET 8 で自作した TUI ファイルマネージャである。Miller カラム型のナビゲーションを持ち、Windows を主対象として CJK 幅処理を自前実装している。Terminal.Gui のような外部 TUI フレームワークは採用しない方針であり、ほぼ全コード(約3800行)が単一の `Program.cs` に収まっている。

現状の主要構造は次の通り。

- **`Column`**: `Path`, `Entries`(`List<string>`), `Selected`, `ScrollOffset` および非同期読み込み状態(`IsLoading`, `ReadCts` 等)を持つ。1つのカラム = 1つのディレクトリの一覧に対応。
- **`ScreenState`**: `ActiveColumn`, `HorizontalScroll`, `PrevFrame`(差分描画用フレームバッファ), `Preview`(`PreviewPane`), `Search`(`SearchState`), `Leap`(`LeapState`)を保持する。
- **`static class Program`**: `List<Column> Columns` と `ScreenState State` を **static グローバルとして1セットだけ**保持する。`MoveUpAsync`, `RebuildRightSideAsync` などのナビゲーション関数群は、引数を取らずにこれらの static フィールドを暗黙に参照して動作する。
- **描画**: `Draw()` が `BuildFrame(width, height)` を呼び、画面全体を表す `Line[]` を構築したうえで文字列配列 `frame[]` にレンダリングする。`BuildFrame` は各カラムを `DrawColumnToLines` で `displayX` オフセット付きに描画し、プレビューペインを右側に追加し、最後にフルパス行(`frame[height - 2]`)とステータス行(`frame[height - 1]`)を上書きする。`PrevFrame` との行単位差分だけを実際の端末に書き出すことで再描画コストを抑えている。
- **CJK 幅処理**: `CharacterWidth` クラス(`GetStringWidth` / `PadToWidth` / `SmartTruncate`)が全角文字幅を計算し、パディングや省略を行う。
- **入力**: `Main` のメインループが `Console.ReadKey(true)` でキー入力を取得する。分岐の優先順位は `State.Leap.Active` → `State.Search.Active` → 通常キー処理(`HandleSpecialKeyAsync` 等)であり、「モード中は入力を先取りする」というパターンがすでに確立している(`HandleLeapKeyAsync`, `HandleSearchKeyAsync`)。
- **エラー表示**: `_lastErrorMessage`(static な `string?`)にメッセージをセットすると、次回の `BuildFrame` でステータス行に1度だけ表示され、表示後にクリアされる。
- **共有機能**: カーソルメモリ(ディレクトリごとの選択位置記憶)と migemo(`MigemoProvider` によるローマ字→日本語検索)は、カラム集合全体で共有される機能であり、ペインが増えても分割してはならない。
- **テスト**: `Zurari.Tests` に xUnit スタイルのユニットテストがある(`NavigationTests`, `SearchMatchTests` 等)。

この構造に対して、ファイルのコピー/移動機能を追加する。移動元と移動先を同時に見せるには画面の上下分割が要り、衝突時の確認や宛先選択には軽量なダイアログ基盤が要る。したがって、コピー/移動そのものより前に、この2つの土台を整備する必要がある。

## 目的

ファイルのコピー/移動機能を追加する。実現のために以下を先行して整備する。

1. 上下2ペイン分割(トグル式) — コピー/移動元と移動先を同時に表示するため。
2. 軽量ダイアログ基盤(確認 / 1行テキスト入力 / リスト選択) — 削除確認、リネーム入力、衝突解決、宛先選択などに共通して使う部品として。

コピー/移動は**ノンモーダル(バックグラウンドジョブ)実行**とする。zrr のコンセプトは「手触りがよく、待たせない、すばやい操作」であり、ファイル操作中も UI を止めない。設計の移植元として、同作者のプロトタイプ twf(`C:\Users\user\source\repos\panzoux\twf`)で実証済みのジョブ設計を用いる(参照実装: `Services/JobManager.cs`、`Controllers/FileController.cs` の `HandleCollision`/`CheckIfBusy`、`UI/TaskStatusView.cs`)。

## 本来の問いと回答

機能追加を「2ペイン描画」と「コピー処理」の実装として捉えると壊れる。本質的には次の5つの問いに答える必要がある。

### 1. これは画面分割の問題ではなく状態の問題である

現状、ナビゲーション状態(`Columns` + `ActiveColumn` / `HorizontalScroll` / `Search` / `Leap` / `Preview`)は static な1セットしか存在しない。2ペイン化とは「この状態セットを2つ持つ」ことであり、「画面を2分割して描画する」ことは派生的な結果に過ぎない。

**回答**: これらを `Pane` クラスに束ね、インスタンス化可能にする。既存のナビゲーション関数はすべて `Pane` を引数として受け取るシグネチャに変更する。一方で、カーソルメモリ・migemo・エラーメッセージ(`_lastErrorMessage`)は引き続きプロセス全体で共有する static のままとする。ペインごとに分離するのは「今どこを見ているか」の状態であり、「アプリ全体の設定・記憶・通知」ではない。

### 2. 描画はサブ矩形に対応できるか

現状の `BuildFrame` は画面全体の高さを前提に、カラム描画・プレビュー描画・パス行・ステータス行を1つの `Line[]` に直接書き込んでいる。2ペインになると、各ペインは画面の上半分・下半分という「サブ矩形」の中でしか描画できない。

**回答**: 各ペインの描画関数にビューポート(`yOffset`, `height`)を渡せるようにする。合成は次の3層で行う。

1. **各ペインの矩形描画** — 各ペインが自分の `yOffset`〜`yOffset+height` の範囲にカラム・プレビューを描画する。
2. **共有フッター** — パス行とステータス行を画面最下部2行に上書きする(全ペイン共通で1組のみ)。
3. **オーバーレイ** — ダイアログが開いていれば最後に中央ボックスを上書きする。

`PrevFrame` による行単位の差分描画は、この3層合成が終わった最終フレームに対してそのまま適用する。合成のどの層で行が変わったかに関わらず、差分検出ロジック自体は変更しない。

### 3. キーボードは誰のものか

2ペイン+ダイアログという複数の「入力を欲しがる主体」が生まれるが、キー入力の経路は1つしかない。

**回答**: 優先順位を「ダイアログ > フォーカスペインの Leap/Search > フォーカスペインの通常キー」の1系統に固定し、1箇所でルーティングする。ダイアログは Leap/Search と同族の「アクティブなら入力を独占するモード」であるため、新しい入力モデルを発明する必要はなく、既存パターン(`State.Leap.Active` → `State.Search.Active` → 通常キー)の一般化で足りる。非フォーカスペインは常にキー入力を受け取らない。

### 4. ダイアログは別画面かオーバーレイか

**回答**: オーバーレイとする。別画面(画面クリア＋専用ループ)にはしない。`BuildFrame` の最終段階で `Line[]` の該当範囲に中央ボックスを上書き描画する方式にする。これにより差分描画の仕組みをそのまま流用でき、背後のペイン内容が破棄されない。CJK 幅計算は既存の `CharacterWidth` をそのまま再利用する。

部品は次の3つに限定する。ジョブ一覧・操作ログビュー・衝突解決・busy 警告・終了確認も、この3部品の変種・組み合わせで賄い、新たな部品種別は追加しない(進捗の常時表示はダイアログではなくステータス行が担う。「実行モデル」節を参照)。

- 確認ダイアログ(Y/N/Esc)
- 1行テキスト入力ダイアログ
- リスト選択ダイアログ(インクリメンタル絞り込み付き)

最大のリスクは IME 経由の日本語入力である。`Console.ReadKey` は IME 変換中の入力やサロゲートペアの扱いに癖があり、実機でしか確認できない。この経路は新規に作らず、既存の検索入力処理(`HandleSearchKeyAsync` が使っている入力経路)を再利用し、Phase 3 で実機検証を行う。

### 5. コピー/移動は UI の問題ではなくエンジンの問題である

コピー/移動を「キー入力を受けてファイルをコピーする処理」としてダイアログ層に直接書くと、進捗表示・キャンセル・衝突処理が UI コードに絡み合う。

**回答**: 進捗通知(`IProgress<T>`)・キャンセル(`CancellationToken`)・衝突時コールバックを持つ非同期エンジンを UI から分離する。エンジンをジョブ基盤(`JobManager`)に載せてバックグラウンド実行し、UI 層は進捗のスナップショットをステータス行に反映するだけにする(「実行モデル」節)。衝突解決(上書き/スキップ/リネーム)の選択肢提示にはリスト選択ダイアログを使うため、ダイアログ基盤の存在がコピー/移動エンジンの前提条件になる。

## 設計

### 状態設計

`Pane` クラスを新設し、現在 `ScreenState` および static グローバルに散在している「1画面分のナビゲーション状態」をまとめる。

```csharp
sealed class Pane
{
    public List<Column> Columns = new();
    public int ActiveColumn;
    public int HorizontalScroll;
    public SearchState Search = new();
    public LeapState Leap = new();
    public PreviewPane Preview = new();
}
```

`ScreenState` は次の役割のみに縮小する。

```csharp
sealed class ScreenState
{
    public string[]? PrevFrame;
    public int PrevWidth;
    public int PrevHeight;
    public List<Pane> Panes = new();   // 常に1〜2要素
    public int FocusedPane;            // 0 = 上(または単一)ペイン, 1 = 下ペイン
    public bool SplitActive;           // トグル状態
    public DialogState? Dialog;        // 開いているダイアログ(null = なし)
}
```

- 非分割時は `Panes.Count == 1`、`FocusedPane == 0` に固定。
- カーソルメモリ・migemo(`_migemo`)・`_lastErrorMessage` は従来通り static のまま、`Pane` の外側で共有する。
- 既存のナビゲーション関数(`MoveUpAsync`, `MoveDownAsync`, `RebuildRightSideAsync`, `EnterAsync` 等)は、シグネチャの先頭引数に `Pane pane` を追加する形にリファクタリングする。呼び出し側は `Panes[State.FocusedPane]` を渡す。

### 描画設計

`BuildFrame(width, height)` を3層構成に分解する。

1. **ペイン矩形描画**
   - `SplitActive == false`: `Panes[0]` を `yOffset = 0`, `height = height - 2`(フッター2行を除く)でフル描画。
   - `SplitActive == true`: 画面の高さを2分割する。上ペイン `yOffset = 0`, 下ペイン `yOffset = paneHeight`。境界に1行の区切り線を挟む(`paneHeight = (height - 2 - 1) / 2` を基準に上下へ割り振り、端数は下ペインに寄せる)。
   - 各ペインの描画関数(`DrawColumnToLines`, `DrawPreviewToLines` を呼ぶラッパー、たとえば `DrawPaneToLines(Line[] lines, Pane pane, int yOffset, int height, bool focused, int width)`)は、`yOffset` を全書き込み行インデックスに加算するだけで既存の描画ロジックをそのまま使う。
   - **非フォーカスペインの減光**: `focused == false` のとき、通常カラーパレットの代わりに「減光パレット」を使う。ディレクトリ色(通常 ANSI 94)はグレー系 ANSI 90 に差し替える。同様に、選択中カーソルの強調色・その他のテキスト色もそれぞれのグレー系相当に差し替える。SGR 2(dim)は端末実装によって効果が不安定なため使用しない。差し替えは色コード文字列を選ぶテーブルまたは分岐によって行い、`DrawColumnToLines` 系の呼び出し時に「どちらのパレットを使うか」を bool 引数として渡す。
   - フォーカスペインの枠・カーソル表示は従来通り。非フォーカスペインは枠・カーソルの強調表示も行わない(通常テキストと同等の弱い表示)。

2. **共有フッター**
   - パス行(`frame[height - 2]`)は **フォーカスペインの** `GetCurrentFullPath()` 相当の値を表示する。
   - 2ペイン分割時のみ、パス行の先頭にどちらのペインかを示すプレフィックスを付与する。`[^]`(上ペインがフォーカス)または `[v]`(下ペインがフォーカス)。単一ペイン時はプレフィックスを付けない。
   - ステータス行(`frame[height - 1]`)の優先順位は「Leap バー > Search バー > エラー/one-shot メッセージ > ジョブサマリ > 通常ヒント」とする(「実行モデル」節)。Leap/Search の参照先は `Panes[State.FocusedPane].Leap` / `.Search` に変える。

3. **オーバーレイ**
   - `State.Dialog != null` の場合、最後に `Line[]` 上へ中央ボックスを上書きする(詳細は「ダイアログ設計」節)。

`PrevFrame` との行単位差分描画ロジック自体は変更しない。3層合成が終わった `frame[]` を渡すだけで、差分検出は既存コードのままで良い。

単一ペイン・ダイアログなし状態では、旧 `BuildFrame` と全く同じ出力になることを Phase 2 の完了条件とする。

### 入力ルーティング設計

メインループの入力分岐を次の優先順位1本に統合する。

```
if (State.Dialog != null)                         → HandleDialogKeyAsync(key)
else if (FocusedPane.Leap.Active)                  → HandleLeapKeyAsync(FocusedPane, key)
else if (FocusedPane.Search.Active)                → HandleSearchKeyAsync(FocusedPane, key)
else                                                → HandleSpecialKeyAsync(FocusedPane, key)   // 通常キー
```

- ダイアログが開いている間は、フォーカスペインの Leap/Search 状態がアクティブであっても入力は届かない(ダイアログが最優先)。
- `Ctrl+W`(分割トグル)と `Tab`(フォーカス移動)は、ダイアログが開いていない場合に限り通常キー処理の一部として扱う。
- 非フォーカスペインは常に入力を受け取らない。ペイン間で状態が混線することはない。
- バックグラウンドジョブはキー入力を持たない。ジョブからのユーザー問い合わせ(衝突解決など)は**ダイアログ要求キュー**に積まれ、`State.Dialog == null` になったタイミングでメインループが FIFO 順に1つずつ開く(「実行モデル」節)。

### ダイアログ設計

`DialogState` を新設し、3種類の部品を1つの状態機械として表現する。

```csharp
abstract class DialogState
{
    public string Title = "";
}

sealed class ConfirmDialogState : DialogState
{
    public string Message = "";
    // Y/N/Esc のみ。結果は呼び出し元に Action<bool?> で通知(true=Yes, false=No, null=Esc)
}

sealed class TextInputDialogState : DialogState
{
    public string Buffer = "";
    public int CursorPos;
    // 例: リネームの初期値としてファイル名を Buffer にプリセット
}

sealed class ListSelectDialogState : DialogState
{
    public List<string> AllItems = new();
    public List<string> FilteredItems = new();
    public string FilterQuery = "";
    public int Selected;
    // インクリメンタル絞り込み: 入力ごとに SearchHelper.MatchesSearchQuery で AllItems を再評価(migemo 対応)
}

// Phase 8 で追加: ジョブ一覧(リスト選択の変種)。各行にジョブの状態・進捗・ソース→宛先を表示し、
// Enter/Delete で選択ジョブのキャンセル確認、Esc で閉じる
sealed class JobListDialogState : DialogState
{
    public List<BackgroundJob> Snapshot = new();  // 開いた時点+タイマー更新のスナップショット
    public int Selected;
}
```

**ダイアログ要求キュー**: バックグラウンドジョブがユーザーの判断を要するとき(衝突解決など)、「ダイアログの内容 + `TaskCompletionSource<T>`」を lock 保護されたキューに積む。メインループは各 tick で `State.Dialog == null` かつキューが空でないとき先頭を取り出してダイアログを開き、確定/キャンセル時に `TaskCompletionSource` を完了してジョブを再開させる。同時に開くダイアログは常に1つ、順序は FIFO。ジョブ側は `await` で停止しているだけなので、他のジョブは影響を受けず継続する。

- 表示位置は画面中央固定。幅・高さは内容(タイトル・メッセージ長・リスト件数)に応じて自動計算する。
- 描画は `BuildFrame` 最終段階で `Line[]` の該当矩形に直接書き込む。文字幅計算は `CharacterWidth.GetStringWidth` / `PadToWidth` / `SmartTruncate` を再利用する。
- 入力処理(`HandleDialogKeyAsync`)は種類ごとに分岐する。
  - `ConfirmDialogState`: `Y`/`Enter` → true, `N` → false, `Esc` → null。結果をコールバックへ渡してダイアログを閉じる。
  - `TextInputDialogState`: 印字可能文字はカーソル位置に挿入、`Backspace`/`Delete`/矢印キーで編集、`Enter` で確定、`Esc` でキャンセル。**日本語入力(サロゲートペア・IME 確定文字列)を含む文字受け取りの経路は、既存の `HandleSearchKeyAsync` の入力処理をそのまま再利用する**(新規の入力処理は書かない)。
  - `ListSelectDialogState`: 印字可能文字で `FilterQuery` に追加しインクリメンタル絞り込み、`↑`/`↓` で選択移動、`Enter` で確定、`Esc` でキャンセル。絞り込み判定は既存の `SearchHelper.MatchesSearchQuery`(regexMode=false、共有 `_migemo` インスタンス)を再利用し、ローマ字入力で日本語のブックマーク/ヒストリも絞り込めるようにする。対象リストは高々数百件のため、検索モードのようなデバウンスは行わず、キー入力ごとに全件を再評価する。
- ダイアログのライフサイクルは「開く関数(タイトル・初期値・完了時コールバックを受け取る)」→「`State.Dialog` にセット」→「`HandleDialogKeyAsync` が確定/キャンセルで `State.Dialog = null` に戻し、コールバックを呼ぶ」という一方向の流れに統一する。

### コピー/移動エンジン設計

UI から独立した非同期エンジンとして実装する。

```csharp
enum ConflictResolution { Overwrite, Skip, Rename }

// 衝突1件へのユーザーの回答。Rename のときは NewName 必須。
// コールバックが null を返した場合は「ジョブごとキャンセル」を意味する。
sealed record ConflictDecision(ConflictResolution Resolution, string? NewName = null);

// バッチ全体の結果。UI 層はこれを結果サマリの表示に使う
sealed record FileOpResult(int Succeeded, int Skipped, int Failed, string? FirstError);

interface IFileOpProgress
{
    void Report(FileOpProgressInfo info);      // 現在処理中のパス、完了件数/総件数、転送バイト数など
    void ReportItemResult(OpLogEntry entry);   // ファイル1件の結果確定(OK/SKIP/FAIL/CANCEL)ごとに呼ばれる
}

static class FileOpEngine
{
    // sources: 複数件対応。マーク集合(複数件)またはカーソル下の1件を受け取る。
    static Task<FileOpResult> CopyAsync(
        IReadOnlyList<string> sources,
        string destDir,
        IFileOpProgress progress,
        Func<string, Task<ConflictDecision?>> onConflict,
        CancellationToken ct);

    static Task<FileOpResult> MoveAsync(
        IReadOnlyList<string> sources,
        string destDir,
        IFileOpProgress progress,
        Func<string, Task<ConflictDecision?>> onConflict,
        CancellationToken ct);
}
```

- 衝突(宛先に同名ファイル/ディレクトリが存在)時は `onConflict` コールバックを呼び、呼び出し元(UI 層)がリスト選択ダイアログ(上書き/スキップ/リネーム)を表示して結果を返す。エンジン自体はダイアログを知らない。
- 進捗は `IFileOpProgress.Report` を通じて `BackgroundJob` の進捗フィールド(lock 保護)に書き込み、メインループが各 tick のスナップショット読み取りでステータス行に反映する。
- キャンセルは `CancellationToken` で伝播する。詳細な意味論は次の「実行モデル」節に定める。
- 衝突時の `onConflict` の UI 側実装は、ジョブごとの sticky 選択(「すべて上書き」「すべてスキップ」)を記憶し、2回目以降はダイアログを開かず即答する。sticky はエンジンではなく UI 層(コールバック実装)の責務とし、エンジンの `ConflictResolution` は3値のまま変えない。
- ファイル操作失敗(権限・ロック・パス長など)は例外を捕捉し、`_lastErrorMessage` 経由でステータス行に表示する(新しいエラー表示経路は作らない)。
- ディレクトリのコピー/移動は再帰的に行い、進捗はファイル単位で報告する。

### 実行モデル(ノンモーダル・ジョブ方式)

コピー/移動は**ノンモーダル(バックグラウンドジョブ)実行**とする。実行中も UI はブロックされず、ナビゲーション・検索・Leap・別のファイル操作を通常通り行える。zrr の「待たせない」コンセプトの中核であり、設計は twf で実証済みのパターンを本アプリの単一ループ構造に翻訳したものである。

**ジョブ基盤(JobManager / BackgroundJob)**

- `BackgroundJob`: 連番 `ShortId`、操作種別(コピー/移動)、状態(`Pending → Running → Completed | Failed | Cancelled`)、進捗(完了件数/総件数、転送バイト数、現在処理中のファイル名)、`CancellationTokenSource`、busy 判定用のソースパス群と宛先ディレクトリ、完了時の `FileOpResult` を持つ。
- `JobManager`: `Program` の static 共有とする(ペインに属さない)。lock 保護された `List<BackgroundJob>` と `SemaphoreSlim`(同時実行数 **4**、twf の実証値)を持つ。`StartJob` はジョブを登録して `Task.Run` で即座に制御を返す。上限超過分は `Pending` のまま順番待ちする。完了系(Completed/Failed/Cancelled)のジョブはセッション内で直近20件まで保持する。
- **スレッド境界**: 進捗フィールドへの書き込みはジョブスレッド、読み取りはメインループ。既存の `_searchLock` と同じ「lock + スナップショット」方式で保護する。ペイン/カラムの状態(`Columns`、`Entries` 等)にジョブスレッドは**一切触れない** — 画面への反映はすべてメインループが行う。

**開始と進捗表示**

- `c`/`m` はジョブを登録した瞬間に制御を返し、「コピー開始: <名前> → <宛先> (#N)」を one-shot ステータスに表示する。UI は一切待たない。
- ステータス行の優先順位を「Leap バー > Search バー > エラー/one-shot メッセージ > **ジョブサマリ** > 通常ヒント」と定める。ジョブサマリはアクティブジョブがあるときのみ表示し、「▶2件実行中 #3 コピー 45% (12/40) <現在のファイル名>」のように件数+最古の実行中ジョブの進捗を示す。
- イベント通知は使わず、メインループによる**ポーリング**とする。反映レイテンシは経路ごとに次の3段階に定める。
  1. **ユーザー操作起因の描画** — スロットリング対象外。キー処理直後のループパスで描画する(現行ループの挙動そのまま。キー→描画は実質即時)。本節のポーリング間隔は操作の応答性に一切影響しない。
  2. **ジョブの状態遷移**(完了・失敗・キャンセル・衝突要求の発生)— スロットリング対象外。次のループパスで反映する(無入力時でも最大50ms後)。
  3. **連続量の表示更新**(進捗率・件数・バイト数・現在ファイル名)— 前回反映から**100ms 以上経過**を条件とする時刻ベースの間引き。Windows のタイマ/スリープ精度は既定で約15.6ms粒度であり、100ms 未満の周期保証は不正確または高負荷になるため、100ms 未満の更新は仕様として要求しない。
- メインループの周期(現在は無入力時 50ms スリープ)が将来変わっても本仕様は影響を受けない。(twf のイベント+タイマー2段構成は Terminal.Gui 用の翻訳前形態と位置づける)

**衝突解決(ダイアログ要求キュー経由)**

- エンジンが衝突を検出すると、`onConflict` の UI 側実装がダイアログ要求キューに「衝突解決ダイアログ + `TaskCompletionSource`」を積み、当該ジョブは `await` で停止する。他のジョブは継続する。
- 衝突解決はリスト選択ダイアログで行い、選択肢は「上書き / すべて上書き / スキップ / すべてスキップ / リネーム」。「すべて〜」は当該ジョブ内の sticky として UI 層が記憶し、以降の衝突はダイアログなしで即答する。「リネーム」はテキスト入力ダイアログ(初期値=衝突したファイル名)を続けて開く。衝突解決ダイアログの `Esc` は**そのジョブのキャンセル**を意味する。
- **外部変更と失敗の意味論**: 転送中の I/O 失敗(ソース消失・ロック・アクセス拒否など)は、当該ファイルを「失敗」として記録し、宛先に部分ファイルがあれば削除したうえで、**残りのファイルへ継続する**(ディレクトリ再帰コピー中の個別ファイルも同じ規則)。バッチ全体は中断しない。結果サマリには失敗件数と最初の失敗メッセージを含める(例: 「コピー: 2件完了 / 1件失敗: <メッセージ>」)。
- **衝突判定のタイミング**: 宛先の同名チェックは事前スキャンではなく、ファイルごとのコピー直前に行う。判定からコピー実行までの間に外部プロセスが同名ファイルを作成した場合(TOCTOU)は、上書きなしコピーの失敗を衝突として扱い、通常の `onConflict` コールバックに合流させる。専用の排他機構は設けない。

**アプリ内操作の調停(busy 警告)**

- ノンモーダルでは、実行中ジョブのソース/宛先にユーザーが新たな操作(`c`/`m`/`d`/`r`)を行うことが構造的に可能になる。これは強制ブロックせず、`JobManager.GetBusyPaths()`(アクティブジョブのソースパス群+宛先ディレクトリ)と新規操作の対象パスが重なる場合に、確認ダイアログ「実行中のジョブが対象パスを使用しています。続行しますか?」を出してユーザーの判断に委ねる(twf の `CheckIfBusy` 方式)。重なり判定はパスの前方一致(ディレクトリ配下を含む)、`OrdinalIgnoreCase`。
- 警告を無視して続行した結果の競合(ソース消失など)は、上記「外部変更と失敗の意味論」(ファイル単位で失敗記録して継続)が受け止める。調停は「防止」ではなく**「警告 + 失敗許容」の2段構え**とする。

**キャンセル**

- `Shift+J` でジョブ一覧ダイアログ(`JobListDialogState`)を開く。各行にジョブの状態・進捗・ソース→宛先を表示し、`Enter` または `Delete` で選択ジョブのキャンセル確認 → `CancellationTokenSource.Cancel()`。一覧の `Esc` はダイアログを閉じるだけ。
- キャンセルの意味論: 完了済みファイルは確定しロールバックしない。キャンセル時点で転送中だった1件は宛先の部分ファイルを削除する。キャンセル後は one-shot ステータスに「キャンセル: N/M件完了」を表示する。

**アプリ終了時の手当**

- 通常終了(`Esc`)時にアクティブジョブがあれば、確認ダイアログ「実行中のジョブがN件あります。すべてキャンセルして終了しますか?」を出す。Yes → 全ジョブに `Cancel` を要求し、最大5秒待機してから終了する。No/Esc → アプリに戻る。
- `Main` の `finally` でも保険として同じ処理(全 Cancel + 最大5秒待機)を行う。端末ウィンドウのクローズ等によるプロセス強制終了では宛先に部分ファイルが残り得るが、これは許容し、次回起動時の検出・自動清掃は行わない(twf は終了時チェックを持たないが、本アプリでは確認を入れる)。

### 操作ログ

デバッグと事後確認(どの操作・ジョブ・パス・ファイルで何が起きたか)を追跡可能にする。ジョブ一覧(直近20件)が「ジョブ単位の要約」、操作ログが「ファイル単位の全記録」という役割分担とする。

- `OperationLog`(`Program` の static 共有、lock 保護)。1エントリ = タイムスタンプ、ジョブ番号(同期操作は `-`)、操作種別(COPY/MOVE/DELETE/RENAME)、結果(OK/SKIP/FAIL/CANCEL)、ソースパス、宛先パス、メッセージ(失敗理由など)。
- 記録先: メモリ上のリングバッファ(直近1000件)+ `%APPDATA%\zurari\operations.log` への追記(1行1エントリのプレーンテキスト、セッションをまたいで蓄積)。10MB 超過時に `operations.log.1` へローテートする(保持は1世代のみ)。
- 記録契機: 同期操作(削除・リネーム)は操作完了時に UI 層が記録する。ジョブは `IFileOpProgress.ReportItemResult`(ファイル1件の結果確定ごとにエンジンが呼ぶ)を UI 層実装が受けて記録する。エンジン自身はログの存在を知らない。
- 参照: `Shift+L` で操作ログビューを開く(リスト選択ダイアログの読み取り専用変種。新しい順に表示。インクリメンタル絞り込みは migemo 対応の共通実装をそのまま使う)。

### 完了後のフィードバックとペイン再読込

- ジョブ完了(全件成功・一部スキップ・キャンセル・失敗)時、結果サマリを既存の `_lastErrorMessage` 経路(one-shot)でステータス行に表示する(例: 「コピー完了: 1件」「移動 #3: 2件完了 / 1件失敗: <メッセージ>」)。
- **影響カラムのみ再読込する**: 全ペインの全カラムのうち、`Path` が宛先ディレクトリまたは各ソースの親ディレクトリと一致(`OrdinalIgnoreCase`)するカラムを再読込し、`CachedChildren` を無効化して `RebuildRightSideAsync` を再実行する。無差別な全ペインリフレッシュは行わない(ユーザーが操作中のペインを不必要に触らないため。モーダル案では全リフレッシュとしていたが、ノンモーダルでは実行中・完了時の再読込がユーザー操作と並走するため、影響範囲の限定が必要になる)。
- **タイミング**: ジョブ完了時に必ず1回。加えて実行中は **500ms** スロットリングで影響カラムを再読込し、コピー先を表示しているカラムにファイルが増えていく様子が見えるようにする(twf の `FileListRefreshIntervalMs` 方式。twf の実証値は1000msだが、体感の許容値 300〜500ms の上限を採る)。再読込の実行主体は常にメインループ(ポーリング処理内、時刻ベースの間隔判定)であり、ジョブスレッドは進捗を書くだけで再読込を直接行わない。
- **保護規則**: 対象ペインで Leap または Search がアクティブな間は自動再読込を行わない(`Entries` の再読込は検索のマッチインデックスや Leap の `VisibleIndices` を破壊するため)。代わりにそのペインを dirty とマークし、モード終了時に再読込する。
- カーソル位置はカーソルメモリと既存の復元ロジック(`RestoreTo` / `SeekRestoreTo`)で維持する。移動・削除で消えたエントリにカーソルがあった場合は、既存の欠落時挙動(近傍への復帰)に従う。
- Phase 4 の削除・リネームは**同期実行のまま**とする(ごみ箱送り・リネームは十分速く、ジョブ化の複雑さに見合わない)。完了後にフォーカスペインの影響カラムを再読込する。大容量ディレクトリの直接削除のジョブ化は今後の検討とする。

## 実装フェーズ

各フェーズ完了時点で、アプリは常に動作する状態を保つ。

- **Phase 1: Pane 抽出リファクタ**
  `Column` の集合と `ActiveColumn` / `HorizontalScroll` / `Search` / `Leap` / `Preview` を `Pane` クラスにまとめ、ナビゲーション関数を `Pane` 引数を取る形にリファクタリングする。`ScreenState` にはフレームバッファ(`PrevFrame` 等)とフォーカス中ペインの参照のみを残す。見た目は変更しない。
  **完了条件**: 既存のユニットテスト(`Zurari.Tests`)がすべて緑のまま。

- **Phase 2: ビューポート描画**
  `BuildFrame` を「ペイン矩形描画 → 共有フッター → オーバーレイ」の3層合成に分解する。見た目は変更しない。
  **完了条件**: 単一ペイン・ダイアログなしの状態で、Phase 1 以前と画面出力(端末に書き込まれるバイト列)が同一であることを確認する。

- **Phase 3: 入力ルーティング一般化 + ダイアログ3部品**
  「ダイアログ > フォーカスペインの Leap/Search > フォーカスペインの通常キー」の優先順位に統合し、確認/1行テキスト入力/リスト選択の3ダイアログを実装する。日本語 IME 入力の実機検証を含む。
  **完了条件**: 3種のダイアログが単独で開閉・確定・キャンセルでき、日本語入力を含むテキスト入力ダイアログが実機で文字化けなく動作する。

- **Phase 4: ダイアログ実証機能**
  単一画面のまま価値が出る機能をダイアログ基盤の上に実装する。
  - 削除(`d` または `Delete`): 確認ダイアログを表示し、Windows ではごみ箱送りを既定動作とする。
  - リネーム(`r`): テキスト入力ダイアログ、初期値は現在のファイル名。
  - ブックマーク(`b` = 一覧からジャンプ、`Shift+B` = 現在ディレクトリを追加): `%APPDATA%\zurari\bookmarks.txt` に永続化する。
  - ヒストリジャンプ(`h`): セッション内の訪問履歴からリスト選択ダイアログで選ぶ。
  - 操作ログ基盤(`OperationLog`): メモリ直近1000件+`%APPDATA%\zurari\operations.log` 追記。削除・リネームから記録を開始する(「操作ログ」節)。
  **完了条件**: 削除・リネーム・ブックマーク・ヒストリジャンプの4機能がすべて実機で動作し、削除・リネームが操作ログに記録され、ユニットテストが緑。

- **Phase 5: 上下2ペイン(トグル式)**
  `Ctrl+W` で分割の開閉、`Tab` でフォーカス移動を実装する。各ペインは独立した Miller カラム群と検索/Leap 状態を持つ。第2ペイン(下ペイン)を開いたときの初期パスは、その時点でフォーカスしていたペインの現在ディレクトリとする。プレビューは各ペイン内で従来ルール通りに動作する。
  **完了条件**: `Ctrl+W` で分割の開閉が往復でき、`Tab` でフォーカスが移動し、両ペインが独立してナビゲーション・検索・Leap を実行できる。非フォーカスペインの減光表示とパス行の `[^]`/`[v]` プレフィックスが正しく切り替わる。

- **Phase 6: 複数マーク**
  「複数マーク設計」節の確定設計を実装する。`Space` トグル+カーソル下移動、`Shift+Space` 全解除、`*`+ANSI 93 表示、再読込時の名前ベース突合、ステータス行の「M件マーク中」。既存の削除(`d`)を「マークがあればマーク集合を対象」に拡張する(確認ダイアログに対象件数を表示)。
  **完了条件**: マークの付与・解除・全解除・再読込耐性が動作する。マーク済み複数ファイルの削除が件数表示付きの確認を経て動作する。ユニットテスト(マーク状態の再読込突合)が緑。

- **Phase 7: コピー/移動(ジョブ基盤コア)**
  `FileOpEngine` と `JobManager` を実装する。コピーは `c`、移動は `m` で、非フォーカスペインのアクティブカラムのディレクトリを宛先として即座にジョブ登録し、制御を返す。対象は「マークがあればマーク集合、なければカーソル下の1件」(複数マーク設計の規則)。進捗はステータス行のジョブサマリに表示する。衝突はダイアログ要求キュー経由で解決する(sticky・リネーム対応)。ファイル1件ごとの結果を操作ログに記録する。ジョブ完了時の影響カラム再読込(Leap/Search アクティブ時は遅延)と、終了時のアクティブジョブ確認を含む。非分割時は宛先をブックマーク/ヒストリから選ぶフォールバックダイアログを表示する(Phase 4 の部品を再利用)。
  **完了条件**: `c`/`m` が UI をブロックせず、実行中にナビゲーション・検索が通常通り動作する。単一ファイル・マーク複数件・ディレクトリ再帰の3パターンでコピー/移動が完了する。進捗がステータス行に表示され、衝突ダイアログ(すべて上書き/すべてスキップを含む)で解決でき、完了時に影響カラムが再読込され結果サマリが表示され、ファイル単位の結果が操作ログに残る。アクティブジョブがある状態の `Esc` で終了確認が出る。エンジン+JobManager のユニットテスト(複数件・失敗継続シナリオを含む)が緑。

- **Phase 8: ジョブ運用 UX**
  `Shift+J` のジョブ一覧ダイアログ(状態・進捗の表示、個別キャンセル、完了ジョブの直近20件履歴)、`Shift+L` の操作ログビュー(絞り込み対応)、busy パス警告(`c`/`m`/`d`/`r` の対象が実行中ジョブのパスと重なる場合の確認)、実行中の 500ms スロットリング再読込を実装する。
  **完了条件**: ジョブ一覧からの個別キャンセルが機能する。操作ログビューで直近の操作結果を参照・絞り込みできる。busy 警告が表示され続行/中止を選べる。コピー先を表示中のカラムにファイルが逐次現れる。

| 印字可能文字 | テキスト入力/リスト選択ダイアログ | バッファ/絞り込みクエリへ追加 |
| `↑` / `↓` | リスト選択ダイアログ | 選択項目の移動 |
| `Enter` | テキスト入力/リスト選択ダイアログ | 確定 |
| `Backspace` / `Delete` / `←` / `→` | テキスト入力ダイアログ | カーソル移動・編集(既存の検索入力処理を再利用) |

平文字キー(`c` / `m` / `d` / `r` / `b` / `h`)は `HandleSpecialKeyAsync` で現在未割当であることを確認済み。zurari は文字入力で検索が始まる仕様ではない(検索開始は `/` のみ)ため、平文字への機能割当は安全である。

Leap モード・Search モード内のキー割当は既存仕様(`2026-06-22-leap-navigation-design.md`, `2026-06-14-quick-search-design.md`)から変更しない。ただしこれらは「フォーカスペインの」Leap/Search として動作する。

## エラー処理とテスト方針

- ファイル操作失敗(権限不足・ファイルロック・パス長超過など)は、既存の `_lastErrorMessage` 経路でステータス行に表示する。新しいエラー表示経路は作らない。
- コピー/移動エンジンは、ファイル単位の失敗を `FileOpResult`(成功/スキップ/失敗の件数と最初の失敗理由)として記録し、残りへ継続する(「実行モデル」節の「外部変更と失敗の意味論」)。バッチ継続が不可能な失敗(宛先ディレクトリの喪失など)のみ例外として呼び出し元へ伝播し、UI 層が `_lastErrorMessage` にセットする。
- ユニットテスト対象は以下の5点とする。
  - ダイアログのレイアウト計算(幅・高さ・中央配置座標が入力サイズに応じて正しく算出されること)。
  - テキスト入力バッファの CJK 幅処理(全角文字混在時のカーソル位置・表示幅計算が `CharacterWidth` の既存ロジックと整合すること)。
  - コピーエンジン(テンポラリディレクトリに実ファイルを作成し、コピー/移動/衝突解決/継続失敗/キャンセルの各シナリオを検証する)。
  - `JobManager`(状態遷移、同時実行上限、busy パス判定の前方一致、キャンセル、完了ジョブ20件保持)。
  - マーク状態(名前ベース突合による再読込耐性、操作対象の組み立て規則「マーク集合 or カーソル下1件」)。
- 描画結果の見た目(減光パレットの配色、オーバーレイの位置合わせ)および IME 入力は手動確認とする。自動テストの対象にしない。

## 複数マーク設計(スコープ内: Phase 6)

当初はスコープ外としていたが、単一ファイル前提ではコピー/移動エンジンの評価・テストパターンが制限されるため、スコープに含める(ユーザー決定 2026-07-06)。以下はすべて確定設計である。

- **状態の持ち方**: `Column` に `HashSet<string> Marked` を追加する(`StringComparer.Ordinal`)。要素は `Entries` の文字列と完全一致(ディレクトリは `/` サフィックス付きのまま)。インデックスではなく名前ベースとすることで、再読込・ソート順変更に耐える。カラム再読込時は `Entries` に存在しなくなった名前を `Marked` から除去する。
- **生存範囲**: マークはカラム(= そのディレクトリの表示)に属する。カラムが破棄されたら消える。ペイン間で共有しない。永続化しない。
- **キー**: `Space` = カーソル下エントリのマークをトグルし、カーソルを1つ下へ移動。`Shift+Space` = アクティブカラムの全マーク解除。Leap/Search モード中の `Space` は各モードの入力であり、マーク操作はできない(既存の入力優先順位に従う)。
- **表示**: マーク行は名前の前に `*` を付け、文字色を ANSI 93(黄)にする。カーソル行がマーク済みの場合はカーソル強調を優先しつつ `*` は残す。非フォーカスペインでは減光規則に従い ANSI 90 で表示し、`*` のみで区別する。名前の表示幅計算では `*` の1桁分を差し引く。
- **操作対象の規則**: `c` / `m` / `d` は「フォーカスペインのアクティブカラムに1件以上マークがあればマーク集合、なければカーソル下1件」を対象とする。他カラム・他ペインのマークは常に無視する。`r`(リネーム)は常にカーソル下1件でありマークを無視する。複数件を対象とする確認ダイアログには対象件数を表示する。
- **実行後**: 成功したエントリのマークは解除する。スキップ・失敗したエントリのマークは維持する(再試行を容易にするため)。
- **ステータス行**: アクティブカラムにマークが1件以上あるとき、通常ヒントに「M件マーク中」を追記する。
- **エンジン**: `FileOpEngine` は既に `IReadOnlyList<string>` を受けるため変更不要。UI 層で対象リストを組み立てる箇所のみ変更する。

## スコープ外・今後の検討

- マークの永続化、範囲マーク(Shift+カーソル等)、ワイルドカードによる一括マークは対象外(`Space` トグルと `Shift+Space` 全解除のみ)。
- コピー/移動の進捗をキャンセル後に途中状態からロールバックする機能は対象外(キャンセル時点までの操作は確定させる。転送中だった1件の部分ファイル削除のみ行う)。
- 3ペイン以上への拡張は対象外(トグル式の上下2ペインのみ)。
- ダイアログの位置・サイズをユーザーがカスタマイズする機能は対象外(自動計算・中央固定のみ)。
- モーダルの進捗ダイアログ方式は採用しない(検討のうえ却下: 「待たせない」コンセプトに反する。ノンモーダルの設計判断4点 — 調停・多重実行・再読込タイミング・キャンセル UI — はすべて「実行モデル」節で回答済み)。
- ジョブの一時停止/再開/優先度変更は対象外(キャンセルのみ)。
- 削除(ごみ箱送り)のジョブ化は対象外(同期実行。大容量ディレクトリの直接削除をジョブ化するかは今後の検討)。
- **メインループのイベント駆動化(待機時 CPU 消費 0)は対象外**。今回はポーリングで確定する。将来検討する場合の論点を書き残す: 変化源のうちジョブは in-process なのでイベント化可能であり、外部プロセスによる変更は現状も手動リフレッシュのみでイベント化の障害にならない。真の障害は (1) コンソール入力に待機可能なイベントがなく、専用スレッドのブロッキング `ReadKey` + イベントキューへの構造変更を要すること、(2) 既存機能のアイドル tick 依存(検索/Leap の 300ms デバウンス、非同期読み込み中の表示更新)の移行が必要なこと。これはジョブ機能ではなくメインループ全体の再設計であり、着手時は別スペックとする(FileSystemWatcher の採否もその際に判断)。

## 実装の実行体制(セッション分離)

本スペックの実装は、実装者(モデル・セッション)の判断力に依存せず、文書の決定性によって品質と進捗を担保する。前提: 実装セッションは安価なモデルによる使い捨て(コンテキストを引き継がない)であり得る。

- **判断は文書に置き、セッションに置かない**: 設計判断はすべて本スペックで確定済みとする。実装中に本スペックおよび計画ファイルに書かれていない判断が必要になった場合、実行セッションは**自分で決めず**、計画ファイル末尾の「未解決事項」欄に論点を記録し、そのステップを保留して停止する。
- **Phase ごとの実装計画ファイル**: `docs/superpowers/plans/2026-07-06-dual-pane-phaseN-<topic>.md` として Phase 1〜8 の各計画を作成する。各計画ファイルは次を含む。
  - (a) **前提条件**: 前 Phase の完了条件を再検証する具体的手順(コマンドと期待結果)。
  - (b) **ステップ**: 変更対象ファイル・関数名・擬似コードレベルの指示。実行者の裁量は「コンパイルが通る書き方の選択」に限定されるレベルまで具体化する。
  - (c) **検証**: 各ステップの検証コマンド(`dotnet build` / `dotnet test`)と、手動確認が必要な項目の具体的な操作手順・期待画面。
  - (d) **完了条件チェックリスト**: チェックボックス形式。
  - (e) **未解決事項欄**: 空欄で用意し、実行セッションが判断保留を記録する場所とする。
- **進捗の永続化**: ステップ完了ごとに git コミットし、計画ファイルのチェックボックス更新を同じコミットに含める。新しいセッションは「本スペック → 該当 Phase の計画ファイル → `git log`」の順に読むことで、判断なしで現在地を特定できる。
